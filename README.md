# مراقب أسعار مكعب (Mokab Price Tracker)

مشروع **منفصل تماماً** عن مشروع تحليل مراجعات فروع مكعب على Google Maps (ذاك في مستودع `Mokab_review`). هذا المستودع غرضه الوحيد: مراقبة أسعار ومنتجات mokab.com والتنبيه عند أي تغيير.

## الهدف

مراقبة يومية لـ **كامل كتالوج منتجات mokab.com** (حوالي 5000 منتج)، مع أولوية مطلقة **للدقة واكتمال التغطية على حساب السرعة** — لا مشكلة لو أخذ التشغيل ساعة أو أكثر.

## شكل التقرير (المطلوب من المستخدم)

التقرير يصل كـ **GitHub Issue** يومي، ومقسّم **حسب الكاتوجري** (تصنيف مكعب الفعلي لكل منتج، المستخرج من `product:category`). تحت كل كاتوجري **ثلاثة جداول**:

1. **💰 تغيّر الأسعار** (زيادة أو نقص) — المنتج | السعر السابق | السعر الحالي | نسبة التغيّر | الرابط
2. **🏷️ العروض** — المنتج | نوع التغيير (بدأ عرض / انتهى العرض / تغيّرت قيمة العرض) | السعر الأصلي | سعر العرض | نسبة الخصم | الرابط
3. **🆕 منتجات تمت إضافتها** — المنتج | السعر | عليه عرض؟ | الرابط

ويسبق ذلك **جدول ملخّص** يعرض عدد التغييرات في كل قسم. المنتجات اللي ما تغيّر فيها شيء **لا تُذكر إطلاقاً**، والقسم اللي ما فيه تغيير لا يظهر أصلاً.

## البنية التقنية (ولماذا هذا التصميم بالذات)

- **لا يوجد Apify ولا مهمة Claude مجدولة** — جُرّب واستُبعد (يكلف ويعتمد على فتح تطبيق Claude). الحل الحالي **GitHub Actions** فقط: مجاني ومستقل عن أي جهاز.
- **الاكتشاف عبر sitemap.xml** — نقرأ `https://mokab.com/sitemap.xml`، نتجاهل خرائط المدونة، ونجمع كل رابط منتج (`.../p<رقم>`) — حالياً ~4999 منتج، ويتحدّث تلقائياً.
- **لا يوجد Playwright** — صفحة كل منتج تضمّن كل ما نحتاجه كـ meta tags في HTML الخام:
  - `product:price:amount` = السعر الأصلي
  - `product:sale_price:amount` = سعر العرض (إذا كان أقل من الأصلي → عليه عرض)
  - `product:availability` = حالة التوفر، `product:category` = تصنيفات المنتج
  فطلب HTTP عادي بـ `requests` يكفي تماماً (بعكس صفحات التصنيفات اللي تحتاج جافاسكربت).
- **توزيع الفحص على 6 شرائح متوازية (أهم قرار للدقة)** — محاولة فحص الكتالوج كاملاً من job واحد أدّت لحظر `429 Too Many Requests` من مكعب. الحل: `strategy.matrix` بـ 6 jobs، كل job يأخذ `sorted(pids)[SHARD_INDEX::6]` (تناوب يضمن خليطاً من كل الأقسام). كل job يعمل على runner مستقل **بعنوان IP مختلف**، فيبقى معدل الطلبات لكل عنوان منخفضاً جداً مع بقاء الزمن الكلي معقولاً.
- **طلب واحد في كل مرة داخل الشريحة + تأخير تكيّفي** — يبدأ بـ 0.6 ثانية بين الطلبات، **يبطئ تلقائياً** عند أي 429 (مع احترام `Retry-After`)، ويعود يتسارع تدريجياً عند النجاح المتواصل، مع جلسة HTTP واحدة (keep-alive).
- **كنسات إعادة المحاولة (sweeps)** — بعد المرور الأول، تُعاد محاولة كل منتج فشل حتى 5 كنسات مع انتظار 90ث بين كل كنسة وتأخير أعلى — وهذا اللي يرفع نسبة القراءة لأقصى حد.
- **لا إنذارات كاذبة أبداً** — المنتج اللي فشلت قراءته **لا يُقارَن ولا يُحدَّث**، وتبقى قيمته القديمة في خط الأساس لتُعاد قراءته في التشغيل القادم. التقرير يذكر نسبة القراءة وعدد ما تعذّرت قراءته بوضوح.
- **تشغيل التأسيس (seeding)** — أول تشغيل على كامل الكتالوج يحفظ المنتجات كخط أساس ويرسل ملخّصاً قصيراً، بدل اعتبار ~5000 منتج "جديدة".
- **حد حجم الـ Issue** — GitHub يحدّ جسم الـ Issue بـ 65536 حرف؛ لو طال التقرير نعرض أكبر عدد ممكن من الأقسام ونرفق التقرير الكامل كـ artifact باسم `full-report`.
- **التنبيه عبر GitHub Issues** — GitHub يرسل بريداً تلقائياً (يتطلب أن يكون إعداد Watch للمستودع = All Activity). **لا يوجد تيليجرام** (مستبعد بطلب المستخدم).

## الملفات

| الملف | الوظيفة |
|---|---|
| `check_prices.py` | فاحص الشريحة: يكتشف كل روابط المنتجات من sitemap، يأخذ نصيب الشريحة (`SHARD_INDEX`/`SHARD_COUNT`)، يفحصها بتأخير تكيّفي وكنسات إعادة محاولة، ويحفظ `shard_<i>.json` |
| `build_report.py` | يدمج كل ملفات الشرائح، يقارن بخط الأساس، ويبني التقرير مقسّماً حسب الكاتوجري بثلاثة جداول تحت كل قسم |
| `mokab_price_baseline.json` | "الذاكرة" — آخر حالة معروفة لكل منتج (الاسم، السعر الحالي، السعر الأصلي، هل عليه عرض، التوفر، الكاتوجري، الرابط) + إحصاءات التغطية |
| `.github/workflows/price-check.yml` | 6 jobs فحص متوازية + job دمج يبني التقرير، يحدّث baseline، ويفتح الـ Issue |

## الجدولة والتشغيل اليدوي

- تلقائياً: يومياً 6:00 صباحاً بتوقيت السعودية (`0 3 * * *` UTC).
- يدوياً: تبويب **Actions** ← **Mokab Price Check** ← **Run workflow**.
- المدة المتوقعة: حوالي 15–40 دقيقة حسب استجابة مكعب (مهلة كل شريحة 300 دقيقة للأمان).
- متابعة التقدّم: سجل كل شريحة يطبع سطر تقدّم كل 100 منتج (مع عدد 429 والتأخير الحالي).

## أفكار لم تُفعّل بعد

- ربط بتيليجرام (بوت + chat_id كـ GitHub Secrets) بدل/بجانب GitHub Issues
- تتبّع تغيّر حالة التوفر (متوفر ↔ نفد) كجدول رابع تحت كل قسم (البيانات محفوظة أصلاً في baseline)
- جدول "كل العروض النشطة حالياً" بدل "العروض اللي تغيّرت" (سيكون طويلاً جداً — يحتاج ملف مرفق بدل Issue)
- رسم بياني لتاريخ السعر عبر الزمن (يحتاج تخزين تاريخي)

## قواعد التعامل مع هذا المشروع

- هذا المشروع **لا علاقة له** بمشروع تحليل مراجعات فروع مكعب (مستودع `Mokab_review`) — لا تخلط بينهما.
- عند أي تغيير جوهري (آلية الفحص، شكل التقرير، قناة التنبيه)، حدّث هذا الملف ليبقى المرجع الكامل.
- إذا ظهر حظر 429 مجدداً: زد عدد الشرائح في `matrix.shard` و`SHARD_COUNT`، أو ارفع `BASE_DELAY` في `check_prices.py`.
